# flexrouter v2 — staged delivery roadmap

**Spec:** `docs/superpowers/specs/2026-09-18-flexrouter-v2-design.md`

The spec is built in stages. One plan per stage, written when that stage starts.
Each stage ends with something that runs.

| Stage | Spec section | Deliverable | Plan |
|---|---|---|---|
| 1 | §1, Migration, open Q3 | One fixed home for settings + keys; `doctor`; dead code removed | `2026-09-18-v2-stage1-shared-home.md` |
| 2 | §2 | Complete OpenAI-shaped surface; library becomes an HTTP client | not yet written |
| 3 | §3 | Per-request trace with `skipped` + verbatim provider messages | not yet written |
| 4 | §5 | Per-key state, benching, cooling, scheduler strategies | not yet written |
| 5 | §4a | Decider protocol, NullDecider, built-in rules, error brain | not yet written |
| 6 | §4b | Model facts + capability state machine | not yet written |
| 7 | §6 | Daily catalogue refresh + pending tray | not yet written |
| 8 | §7 | **Dashboard rebuilt to the approved mock-up — see size note below** | not yet written |
| 9 | §8 | Model ranking runs | not yet written |

**Size note on Stage 8:** every other stage is one contained piece of
background-service logic. Stage 8 is a full visual application (every
provider row, every key row, every model row, live activity strips, a
confidence/provenance rendering system) — closer in scope to several of the
other stages combined than to any one of them. It also cannot really start
until Stages 4 through 7 exist, since it displays their data: key health
(§4), error understanding (§4a), model capabilities (§4b), and the
new/dead-model tray (§6) all have to be real before the dashboard has
anything true to show. Do not plan or estimate it like a normal stage; when
its plan is written, expect it to be broken into its own multi-task
sub-plan rather than a single flat task list.

## Owner decisions taken 2026-09-18 (supersede the spec's open questions)

- **Open Q1/Q2 — the existing `flexrouter.yaml` is NOT migrated.** The owner
  chose to start fresh in the new UI. Stage 1 creates a starter config in the
  fixed home with bucket names only and no models; models arrive via the
  catalogue refresh pending tray (§6) and the models pane (§7). Credentials are
  still lifted across, because retyping keys by hand is the one part of the old
  file worth saving.
- **Open Q3 — delete the superseded modules.** `flexrouter/server.py`,
  `tests/test_server.py`, `flexrouter/dashboard/server.py` and
  `tests/test_dashboard_server.py` are removed in Stage 1.
- **Open Q4 — ship with `NullDecider` as the default** until `typesafe/jev-1.13`
  access and pricing are confirmed. Handled in Stage 5.

## Owner decision taken 2026-09-20

- **Stage 7's catalogue check runs once per service startup per provider, not
  on a daily timer.** The spec originally said "once a day"; the owner
  changed this because a background timer only matters for a service left
  running unattended, and this one is something he starts and stops himself.
  See spec §6 and the Non-Goals entry for "Active health probing" for the
  updated wording.
- **Every internal AI helper (the error-message classifier, the model-facts
  guesser, and the optional self-run model ranking) makes its own direct
  call to its own provider — none of them are routed through flexrouter's
  own routing engine.** A helper that explains what just broke, or judges
  the health of the system, cannot depend on the thing it is diagnosing:
  if the helper had to go through the same routing as everyone else, it
  would be unreachable at exactly the moment every provider is down, and it
  would quietly eat into the same shared free usage it exists to protect.
  See spec §4 and §8 for the updated wording. This is the only place AI runs
  inside flexrouter itself — three uses (classify an error, describe a
  model, rank models) sharing this one rule, not three separate designs.
