# CONTEXT.md

Single-context repo. Glossary of domain terms as the code and docs actually use them. Definitions describe what Stages 1 through 8 have built (the shared home, the OpenAI-shaped surface on one service, the per-request trace, per-key state, the error brain, model facts, the catalogue check, and the dashboard), not later stages of the v2 design.

## Glossary

- **Bucket** — a named list of models your code routes to, e.g. `router.generate(tier="smart")`. Settings files write these under `buckets:`. Called "bucket" rather than "tier" going forward because the owner wants a name that doesn't imply a strict quality ranking between groups. The old name is not gone: `FlexConfig.tiers` is still the field name internally, `cfg.tiers` is how code reads it, and a settings file may still use `tiers:` instead of `buckets:` — `load_config` reads `buckets:` first and falls back to `tiers:` if `buckets:` is absent (`flexrouter/config.py`, `_bucket_key` in `flexrouter/overrides.py`). The public `FlexRouter.generate()`/`agenerate()` parameter is also still named `tier`. On the wire a bucket is named plainly (`smart`); the older `auto-smart` and `smart::provider/model` spellings are still accepted on input and are no longer advertised (`flexrouter/wire.py`, ADR 0009). Asking for a bucket name that does not exist is an error naming the buckets that do, not a quiet fall-through to the first one. Every install also has a built-in `all` bucket — every model in every bucket, once each — unless the owner names one `all` themselves (`ALL_BUCKET` in `flexrouter/wire.py`, ADR 0019).
- **Pinned model** — a request naming `provider/model` instead of a bucket goes to exactly that model, with no failover to another. Served by a second routing engine over a one-model-per-bucket shadow config sharing the live rate-limit, status and quota stores (`LocalRouter._build_pin_engine`).
- **The service** — the one process, on port 4891 by default and bound to `127.0.0.1`, that does all the routing for this machine (`flexrouter serve`, `flexrouter/app.py`).
- **The client library** — `FlexRouter`, which sends requests to the service and never routes (`flexrouter/_client_router.py`). Its method signatures are unchanged, so existing code keeps working, but the service must be running. `LocalRouter` in `flexrouter/_router.py` is the routing code the service runs; importing it and using it directly reintroduces the per-project state this design removed.
- **Local key** — the optional password an app must send as `Authorization: Bearer ...` to use the chat surface. It comes from one of two places, checked in this order (ADR 0015): an **app password** generated from the dashboard's Settings page, stored in `keys.json` like every other credential and shown once when it is made (`flexrouter/app_password.py`: `effective`); otherwise `auth_token` in settings. The tool never writes `auth_token`, it is masked wherever settings are shown, and it is not overridable from the dashboard. It guards the chat surface only; the dashboard and its data stay open on this machine (ADR 0009).
- **Provider** — an upstream LLM API (e.g. `openai`, `groq`), declared under `providers:` with a `base_url` and, optionally, key references.
- **Model** — one entry in a bucket: a `provider` + a `model` id, plus its score, rate limits, and context window.
- **Key** — a credential for a provider. Never stored in the settings file. Lives in `keys.json` in the home, added with `flexrouter keys add <provider>` (`flexrouter/keys.py`).
- **Per-key state** — `state/key_state.json`, keyed by `provider:key_id`, survives restart (`flexrouter/key_state.py`: `KeyStateStore`). Replaces the old blind `counter % len(keys)` rotation: a rejected key is Needs you by itself, not the whole provider — the provider itself only becomes Needs you once every configured key for it is Needs you or off. A rate-limited key is Busy for the provider's own retry-after, else 60s, instead of re-entering rotation immediately. Keys use the same status words as models (see **Status**); a `key_state.json` written before v2.3, with `live`/`cooling`/`benched`/`disabled`, is translated on load. Which live key answers a request is chosen by a `Scheduler` (`flexrouter/scheduler.py`: `pick_key`) — `most_headroom` (default), `round_robin`, `fastest`, or `weighted`, configurable per provider (`ProviderConfig.key_strategy`). None of this touches `engine.py`: key selection happens in `LocalRouter`, after `engine.select()` has already picked a model, by overriding the `api_key` field a `RouteResult` already has (ADR 0011).
- **The home** — the one fixed directory every flexrouter installation on a machine shares: settings, keys, dashboard overrides, and state all live there. Located by `flexrouter/home.py`: `FLEXROUTER_HOME` if set, else a platform default (`%LOCALAPPDATA%\flexrouter` on Windows, `$XDG_CONFIG_HOME/flexrouter` or `~/.config/flexrouter` elsewhere). Replaces the old per-project cwd search.
- **Request trace** — one JSON object per request, appended to `state/traces.jsonl`, rotated daily (`flexrouter/traces.py`: `TraceWriter`). Every model the router considered but could not use is in `skipped`, taken from `RoutingEngine.explain_unavailable()` without any change to `engine.py`. Every attempt against a provider is in `attempts`. `provider_message` and `skipped[].detail` are scrubbed the same way a status reason is (`flexrouter/redact.py`), not literally verbatim, despite the design doc's wording — nothing unscrubbed is ever written to this file. `key_id` is populated with the real key identifier whenever a key was used, now that the per-key state stage (Stage 4, `flexrouter/key_state.py`) has landed — that `null` placeholder was reserved specifically for this stage and is no longer always `null`; it stays `null` only when a route used no key at all (e.g. a keyless provider). `verdict` is populated on every attempt now that the error brain (Stage 5, `flexrouter/error_brain.py`) has landed — that `null` placeholder was reserved specifically for this stage and is no longer ever `null` for a real attempt.
- **Settings** — `config.yaml` in the home. Hand-written, never rewritten by the tool; comments and layout survive permanently (`flexrouter/home.py` `STARTER_CONFIG`, `flexrouter/config.py`).
- **Overrides** — `overrides.json` in the home. Anything changed through the dashboard is written here instead of into settings, then merged over the parsed settings at load time (`flexrouter/overrides.py`: `apply_overrides`). Sections: `settings`, `providers`, `models` (patches to something `config.yaml` already declares), plus `new_providers`, `new_buckets`, `new_models` (additive — a provider, bucket, or model `config.yaml` has never heard of at all; `overrides.add_provider`/`add_bucket`/`add_model`). Each patch section has an allow-list of fields that may be overridden (`overrides.ALLOWED_FIELDS`); a model's `provider` and `model` are its identity and are deliberately excluded there — rewriting them would silently turn an override for one model into a different model, which is exactly what the additive `new_models` section exists to avoid needing. No credential field is overridable from any section. Anything arriving from the dashboard is checked against `ALLOWED_FIELDS` and nothing is written unless it passes, because an override `load_config` cannot read would wedge settings loading permanently and the settings file may not be rewritten to undo it. `flexrouter config reset [section [name]]` clears an existing patch again (a whole provider's or model's overrides at once, not a single field).
- **State** — the `state/` subdirectory of the home: rate-limit windows, per-model statuses (`status.json`), per-key state, the error brain, audit log, health history. Machine-written, safe to delete (it will be rebuilt), and not meant to be hand-edited.
- **Catalogue refresh** — `flexrouter refresh` (`flexrouter/refresh.py`: `refresh_config`, over the provider registry and `/v1/models` lookup in `flexrouter/catalogue.py`), querying each configured provider's model list and comparing it against the settings file. It only records what it found — models that appeared, models that vanished, rate limits or context windows that changed — to `state/catalog_pending.json`, keyed by provider with when each was checked. It never writes `config.yaml` or `overrides.json` itself. `RefreshResult` (`added`/`removed`/`changed`) describes these same findings, not anything applied. It reaches each provider with the credential the rest of the code would use (saved key, then environment variable, then a key typed into settings) and reads the same `buckets:`-then-`tiers:` spelling `load_config` does. A provider whose catalogue call failed counts as **not checked**: it is left out of the comparison and out of this run's pending entries, and whatever an earlier run recorded for it is carried forward, so a provider being down never reads as “all clear”. Two things happen once per service start, in addition to the manual `flexrouter refresh` and the dashboard's refresh button (`flexrouter/_router.py`: `LocalRouter._run_startup_catalogue_refresh`); a failure in either is logged and otherwise ignored, never blocking the service from starting. Always: `refresh_known_model_ids` reads each provider's real model list, caching the ids so a mistyped or vanished model can be recognised and offered a “did you mean” (`flexrouter/catalogue.py`), and flags configured ids the provider no longer lists to `state/unknown_configured_models.json` — it writes nothing to a bucket. Only when the `auto_add_models` setting is on (off by default; formerly `experimental_model_discovery`; ADR 0021, which amends ADR 0014): the full comparison above, staging what it finds into `catalog_pending.json` and recording each newly-discovered model's published context window to `state/model_facts.json` (`ModelFactsStore.record_discovered`). The dashboard's Models page (see **Dashboard** below) can now accept or reject each pending entry by hand — an appeared model into a bucket the owner picks, a vanished model via the ordinary `enabled: false` override, a changed field applied as an ordinary field override (`flexrouter/dashboard/pending_actions.py`) — closing the gap ADR 0014 left open. There is still no automatic apply-on-refresh.
- **Hot reload** — the running service's `LocalRouter` picks up configuration changes on the next request, with no restart. It watches every file the configuration can come from — settings, overrides and keys (`_watched_paths` in `flexrouter/_router.py`) — and compares a fingerprint of each file's `st_mtime_ns` and size, not a single newest timestamp, because a coarse filesystem clock makes two same-tick writes read as identical and `max()` hides a file being replaced by an older copy (ADR 0008). A reload that fails leaves the previously loaded settings in place and serving, recording the reason on `_reload_error`; a broken edit never fails a request in flight. Beyond an error line in the log, nothing surfaces that stale state to the owner yet.
- **Score** — an integer 1–100 on a model entry. Higher is preferred; under the default `smartest` strategy the engine picks randomly among models within 20% of the top available score in a bucket (`flexrouter/engine.py` `_pick`). A bucket can be set to `fastest` (`FlexConfig.bucket_strategy`), which ranks by measured tokens per second instead, inside the same 20% window.
- **Preset** — a template for a provider the owner has not configured yet: base URL, signup link, model-list path, header parser, and seed rate limits (`flexrouter/presets.py`: `Preset` dataclass). Shipped presets live in `flexrouter/data/presets.json` (11 providers at launch: groq, cerebras, openrouter, mistral, nvidia, googleai, deepseek, siliconflow, sambanova, llm7, ollama). The owner can add or patch entries via a `presets.json` in the home directory; `presets.all()` merges the shipped set with the owner's file, bad entries are reported by `presets.problems()` and dropped rather than raised, and `presets.get(name)` returns a single preset by key. The dashboard's Providers page reads these to show "Add" vs "Open" for each provider and to pre-fill the form when the owner adds a new one.
- **Status** — every model has exactly one status: `ready`, `busy`, `struggling`, `needs_you` or `off` (`flexrouter/status.py`: `Status`, `StatusStore`, persisted to `state/status.json`), carrying one plain-sentence `reason`, an `until` (empty when it will not clear on its own) and at most one suggested `action`. **Busy** is a rate limit or overload (429, 5xx, no answer at all): it clears on its own after the provider's own retry-after, else 60 seconds, and never doubles. **Struggling** is a model that answers badly (an empty reply): it is sidelined for about an hour. **Needs you** is something only the owner can fix (a wrong model id, not on the plan, an empty balance, a rejected key): it has no timer. **Off** is a model the owner turned off; the dashboard's facts layer reports it, because a disabled model is dropped from the live configuration altogether. A model's status is the same whether it is reached through a bucket or pinned. Keys use the same words (`flexrouter/key_state.py`, see **Per-key state**). This replaced the older penalty box (doubling cooldown), 24-hour quarantine, provider-wide quarantine and 7-day auto-bench: *quarantine*, *penalty*, *cooldown*, *benched* and *cooling* survive in older ADRs, commit messages and plan records, and today mean Needs you (quarantine, benched) or Busy (penalty, cooldown, cooling). The first start after upgrading migrates `quarantine.json` and `penalties.json` into `status.json` and sets the old files aside.
- **Error brain** — `state/error_brain.json`, a persistent memory of what unfamiliar provider error text means, keyed by a normalized fingerprint (`flexrouter/error_brain.py`: `ErrorBrain`, `fingerprint`, `classify_by_rule`); each call to a classifier is also appended to `state/decider_calls.jsonl`. Built-in rules classify the unambiguous cases instantly, by status code plus a few known substrings. For 400, 403 and 429 the status rule is only a prior (confidence 0.6) that a classifier may overturn, and only when a classifier is actually configured: with none, the rule answers at full confidence. Text no rule settles is fingerprinted, checked against what has already been learned, and on a real miss handed to a `Decider` (`flexrouter/decider.py`, chosen by `build_decider`): `NullDecider` (always `unknown` at zero confidence; what runs whenever the classifier is disabled or has no key), `HttpDecider` (any OpenAI-compatible endpoint held to a JSON schema), or `DecisionsDecider` (TypeSafe's Jev through OpenRouter's Decisions API). Anything answered below 0.80 confidence is flagged for review, and the owner can overrule any learned entry from the dashboard's Error brain page; a hand-corrected (`manual`) entry is never overwritten again. The verdict now feeds the router in two places: a bare 400 takes its status from it (`status._verdict_failure`) and fails over unless the verdict is `bad_request` (`failover.decide_failover`), and a 400 whose verdict is `bad_key` makes that key Needs you. Every other status decision still comes from the status code alone. This is ADR 0020, which superseded ADR 0012 ("the error brain classifies; it does not decide"). The verdict also lands in `attempts[].verdict` in the request trace (ADR 0010).
- **Failure classification** — what a failed attempt makes the model is decided from the HTTP status and body by `status.classify_failure` and applied by `LocalRouter._handle_provider_error` (`flexrouter/_router.py`). 429, 5xx and no answer at all are Busy. 402, 403, 404 and 410, and a 429 whose quota is zero, are Needs you at once, for that one model only: none of them sidelines a whole provider (ADR 0016). A bare 400 has no answer from its status alone and takes the error brain's verdict instead (see **Error brain**). A rejected key (401) is handled apart, by `_handle_auth_failure`: it makes only that key Needs you, and the provider itself becomes Needs you only once every configured key for it is Needs you or off (ADR 0011). What to do next — try another model, try one with a bigger context window, or hand the error back to the caller — is a separate pure decision, `flexrouter/failover.py`: `decide_failover`.
- **Model facts** — `state/model_facts.json`, one entry per `provider/model`, holding what is actually known about a model's capabilities — vision, tools, reasoning — each tagged `yes`/`doubted`/`no` with where the belief came from (`published`/`observed`/`guessed`/`manual`) and how many contradicting results it has survived (`flexrouter/model_facts.py`: `ModelFactsStore`, `CapabilityFact`). Deliberately separate from `ModelConfig.vision`, the static flag declared in settings that `engine.py` already acts on today — this store is *learned* from real traffic and does not (yet) influence routing. One contradicting failure only ever casts doubt, never certainty (`record_contradicting_failure`); any success is stronger evidence than any failure and restores `yes` outright (`record_success`). A `manual` fact is never touched by either.
- **Dashboard** — the service's web UI (`flexrouter/dashboard/`): pages rendered on the server as plain HTML with no build step, plus a thin layer of vendored JavaScript on top — htmx and idiomorph for live refresh and in-place swaps, motion for entrances, and `static/app.js` for the command palette, side panels, toasts and the Playground. Ten areas, each a real URL (`render.py`: `AREAS`): Overview, Providers & keys, Models, Buckets, Requests, Playground, What's broken, Error brain, Allowance and Settings, plus a Logs page that exists only when the service was started with `--log`. Every write is an ordinary form post to a route in `pages.py`. `facts.py` computes read-only views over a running `LocalRouter`; `pages.py` renders most pages and holds the write routes, with the larger pages split into their own `*_page.py` modules; `render.py` holds the menu's area list and the HTML-escaping helpers, and `ui.py` the shared components. The React/Vite frontend that used to live in `dashboard/frontend/` is gone. Every write to settings lands in `overrides.json` via `flexrouter/overrides.py`, never in `config.yaml` (credentials go to `keys.json`); a page reads through `LocalRouter._maybe_hot_reload()` first so a write is visible on the very next page load without restarting the service. "What's broken" and the Overview's "wants you" strip both read `facts.broken()`, which sorts every model and key that is not Ready, and every error-brain entry flagged for review, into two piles: what only the owner can fix, and what the service is already handling on its own. A key's "Test" button (`flexrouter/dashboard/keytest.py`) sends one real chat completion through `flexrouter.client.AsyncClient`, deliberately not a model-list lookup — a key can pass a `/models` check and still fail on every real request (the Cerebras case).
- **Terminal UI** — `flexrouter tui` (`flexrouter/tui/`), the router's terminal surface, a Textual app in four tabs (Overview, Keys, Requests, Doctor). Unlike the dashboard it never builds a `LocalRouter` and needs no service running: it reads the home's own files — `config.yaml`, `keys.json`, `overrides.json`, and what the service wrote under `state/` (`health.json`, `audit.csv`, `traces.jsonl`) — through `flexrouter/tui/facts.py`, mirroring the dashboard's `facts.py`/`render.py` split but file-based rather than router-based. It repaints on a timer and only ever writes a key the owner adds or removes on purpose in the Keys tab. `flexrouter/tui/render.py` is also where the ordinary commands are styled (rich tables, panels, colour), and that is what keeps a piped `flexrouter doctor` byte-for-byte greppable: when the output is not a terminal the console is built wide with no wrapping, so a path or a key id is never folded across two lines. Secrets follow the project's one rule — only `keys.mask()` output is ever rendered. The click CLI (`flexrouter/cli.py`) stays for now and is being phased out in favour of the TUI, one command group at a time, recorded in commit messages and plan records.

## Not yet built

The v2 design (`docs/superpowers/specs/2026-09-18-flexrouter-v2-design.md`) describes nine stages. Stages 1 through 8 are implemented: the shared home, the OpenAI-shaped surface, the per-request trace, real per-key state, the error brain, model facts, the catalogue check, and the dashboard. Stage 8 has no ADR yet — its rulings live in `docs/superpowers/plans/2026-09-21-v2-stage8-dashboard-roadmap.md` until one is written. Ranking models with an AI is built only in its copy-paste form: the Models page's Rank view builds a prompt from the current model list and any benchmark notes the owner adds, then parses the answer pasted back into proposed scores the owner applies row by row (`flexrouter/dashboard/ranking.py`, `/models_catalog/rank`). The service sending that prompt to a model itself is not built. Stage numbers in this file follow the per-stage plans in `docs/superpowers/plans/`; `PLAN-V2.md` numbers the same work as eight steps in a different order (its step 4 covers Stages 5 and 6, step 5 is Stage 4, step 6 is Stage 7, step 7 is Stage 8, and step 8, ranking, is Stage 9). Do not treat later-stage concepts (anything not covered above) as present in the code.
